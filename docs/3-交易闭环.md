# learn-backend 第三轮考核：电商业务与下单闭环

> 本轮在第二轮用户域的基础上，引入商品域和交易域，完成“用户登录 → 浏览商品与 SKU → 加入购物车 → 提交订单”的下单链路。

本轮只包含 **用户、商品、交易** 三个业务域。支付、活动、独立库存、仓库、履约等领域全部后移。

需要特别说明：本轮完成的是“下单闭环”，不是包含支付、发货和售后的完整电商交易闭环。订单创建成功后只代表系统接受了用户的购买请求，不能伪造“已支付”或“已发货”等业务事实。

本轮继续支持 **Java** 和 **Go** 两条技术路线，并在第二轮项目上持续迭代，不重新创建无关项目。

## 知识点

- 用户、商品、交易三个业务域的职责和依赖方向；
- 类目、商品、SKU、基础价格和上下架；
- 购物车、订单、订单明细和订单快照；
- 一对多、多对多关系及中间实体；
- 金额类型、服务端计价和金额校验；

- 身份认证与订单、购物车的资源权限；
- 分页、筛选、排序和必要索引；

### Java 路线

## 业务边界

本轮只允许以下三个业务域：

```text
用户域
  提供当前用户身份和收货地址
       ↓
商品域
  提供商品、SKU、价格和可售状态
       ↓
交易域
  管理购物车、订单和订单明细
```

实际依赖不是简单的上下层关系，而应遵守以下约束：

- 用户域拥有用户资料和收货地址；
- 商品域拥有类目、商品、SKU、价格和上下架状态；
- 交易域拥有购物车、订单和订单明细；
- 交易域可以通过用户域公开能力获取当前用户和地址；
- 交易域可以通过商品域公开能力查询 SKU、价格和可售状态；
- 用户域和商品域不能反向依赖交易域；
- 交易域不能绕过商品域直接修改商品数据；
- 各域不能直接调用其他域内部的 Repository 或操作其私有数据表。

本轮采用模块化单体即可，不要求拆成独立部署的微服务。

## 任务

本轮分为三个阶段。请按顺序完成，并使用 Git Commit 或 Tag 保存关键节点。

### 第一阶段：完善用户域

继续使用第二轮完成的注册、登录和身份认证，不重新实现一套用户系统。

本轮补充交易所需的用户能力：

- 新增、查询、修改和删除自己的收货地址；
- 设置或识别默认收货地址；
- 交易模块能够从可信认证上下文获取当前用户；
- 用户只能查看和操作自己的购物车、地址和订单；
- 订单创建后，用户修改地址不能改变历史订单中的收货信息。

收货地址属于用户域；订单中保存的是下单时使用的地址快照，两者不能混为同一条可变记录。

### 第二阶段：商品域

#### 类目与商品

至少完成：

- 商品类目的创建、修改、查询和停用；
- 商品的创建、修改、查询、上架和下架；
- 普通用户可以分页浏览已上架商品并查看详情；
- 管理员可以维护类目和商品；
- 商品停用或下架时，明确现有 SKU 的处理规则。

#### SKU 与基础价格

一个商品可以拥有多个 SKU。SKU 表示可以被选择、加入购物车和下单的具体规格。

至少完成：

- 为商品创建和维护 SKU；
- SKU 具有可识别的规格信息、唯一业务编码、基础价格和可售状态；
- 普通用户只能选择正常可售的 SKU；
- 管理员可以修改 SKU 价格和可售状态；
- 商品详情能够展示商品及其可售 SKU。

本轮不建立独立库存域。可以使用“是否可售”或简单数量字段辅助测试，但不要求库存锁定、扣减、释放、防超卖、多仓或库存流水。

#### 商品模块边界

商品域应提供稳定的查询能力，让交易域获得下单所需的 SKU 信息。交易域不能直接读取商品模块内部的数据访问对象，也不能自行修改 SKU 价格和状态。

需要思考并记录：

- 商品和 SKU 为什么分开；
- 哪些字段属于商品，哪些字段属于 SKU；
- 商品、SKU 被下架或停用后，购物车和历史订单分别如何处理；
- 为什么历史订单不能每次展示时重新读取当前商品名称和价格。

### 第三阶段：交易域与下单闭环

#### 购物车

至少完成：

- 将可售 SKU 加入当前用户购物车；
- 查询购物车；
- 修改购买数量；
- 删除购物车项；
- 选择部分或全部购物车项提交订单；
- 商品或 SKU 下架后，购物车能够明确标记或拒绝继续提交。

购物车只保存用户当前的购买意图。购物车中展示的价格是查询时价格，不是最终成交价格。

#### 创建订单

创建订单时必须由服务端完成：

1. 从认证上下文获取当前用户；
2. 校验收货地址属于当前用户；
3. 读取用户本次选择的购物车项；
4. 通过商品域重新检查商品和 SKU 的可售状态；
5. 通过商品域重新获取 SKU 当前价格；
6. 校验购买数量；
7. 计算每条订单明细金额和订单总额；
8. 创建订单和订单明细；
9. 记录商品、SKU、成交单价和收货地址快照；
10. 只处理本次已经提交的购物车项。

不得信任客户端提交的 userId、商品名称、单价、订单总额和订单状态。

#### 订单与订单明细

订单至少应能够表达：

- 所属用户；
- 订单编号；
- 下单时间；
- 订单总额；
- 收货信息快照；
- 当前订单状态。

订单明细至少应能够表达：

- 商品和 SKU 标识；
- 商品名称与 SKU 规格快照；
- 成交单价；
- 购买数量；
- 明细金额。

订单总额必须能够根据订单明细重新计算并验证。金额不得使用容易产生不可控误差的二进制浮点类型。

#### 订单状态

本轮只维护订单自身的简单状态，例如：

```text
CREATED → CANCELLED
```

你可以根据项目需要增加其他订单自身状态，但不能添加没有真实业务支撑的 `PAID`、`SHIPPED`、`DELIVERED` 等状态。

后续引入支付、库存和履约时，应分别建立对应领域的状态，不能继续把所有事实塞进一个订单状态字段。

#### 事务与重复提交

- 创建订单、订单明细和处理本次购物车项应具有明确的本地事务边界；
- 其中任一步失败时，不能留下没有明细的订单或只写入一部分明细；
- 同一个下单请求重复到达时，不能无提示地创建多笔相同订单；
- 可以使用请求唯一标识、数据库唯一约束和幂等结果记录等方案；
- 需要通过测试证明事务回滚和重复提交处理有效。

#### 查询与取消

- 用户可以分页查询自己的订单并查看订单详情；
- 用户不能查看或操作其他用户的订单；
- 用户可以取消允许取消的订单；
- 已取消订单不能被重复取消或恢复到未定义状态；
- 取消订单不处理退款、库存返还和履约撤销，这些领域尚未引入。

## 业务不变量

以下规则是本轮验收重点：

1. 用户只能操作自己的地址、购物车和订单；
2. 购物车项和订单明细引用具体 SKU，而不是只有商品；
3. 商品或地址后续变化不能修改历史订单快照；
4. 订单金额完全由服务端根据成交单价和数量计算；
5. 订单总额必须能够由订单明细复核；
6. 订单、订单明细和购物车处理不能出现部分成功；
7. 重复提交不能产生无法解释的重复订单；
8. 商品域不依赖交易域，用户域不依赖交易域；
9. 交易域不能直接修改用户域和商品域的私有数据；
10. 系统不能记录尚未发生的支付、发货和签收事实。

## 测试要求

至少覆盖以下场景：

- 管理员创建类目、商品和多个 SKU；
- 普通用户浏览已上架商品；
- 普通用户不能执行商品管理操作；
- 商品或 SKU 下架后不能正常加入购物车或提交订单；
- 用户只能操作自己的购物车、地址和订单；
- 创建订单时服务端忽略客户端伪造的价格和 userId；
- 商品改价或用户修改地址后，历史订单快照不变；
- 多条订单明细金额与订单总额一致；
- 创建订单中途失败时，事务完整回滚；
- 重复提交同一请求时不会产生无法解释的重复订单；
- 订单取消状态转换正确；
- 数据库迁移能够从第二轮结构升级到第三轮结构。

测试数量不是评分重点，业务边界、不变量和失败路径是否得到验证才是。

## 提示

- 第三轮先把用户、商品和交易三个域做正确，不要提前加入支付和履约；
- 商品是展示和归类概念，SKU 才是用户实际选择和下单的对象；
- 购物车价格只是当前展示，创建订单时必须重新查询并由服务端计价；
- 订单快照用于保存交易发生时的事实，不能被当前商品和地址数据覆盖；
- 金额可以使用定点十进制或最小货币单位整数；
- 本地事务只能保证同一数据库事务范围内的原子性；
- 幂等不是简单地返回错误，而是让相同业务请求重复到达时保持可解释结果；
- 不要为了“解耦”提前拆成微服务，模块边界清晰优先；
- AI 适合解释、评审和排错，不能替代业务规则与测试；
- README 中应如实记录未完成内容和已知问题。
