# learn-backend 第四轮考核：完整电商与工程实践

## 项目描述

### 关于项目：小店开始忙起来了

上一轮，小店已经能展示商品、接收订单。这一轮要把订单继续往下处理：活动期间卖多少钱，仓库还有多少货，用户是否付了款，商品有没有发出，都需要在系统中有对应的操作和记录。

同时，小店不再只有你一个人在点按钮。周边上新时可能有很多人一起下单，后台工作可能变慢，外部通知也可能延迟或失败。你需要把已有项目补成一个完整的基础电商系统，再选择其中一个常见功能深入完成，用真实业务中的异步、重试、并发处理和压测支撑它。

本轮继续使用第三轮项目，保留已有账号、商品、购物车、地址和订单功能。支付与物流使用本地模拟，单个仓库即可完成基础流程，不要求真实商户资质、付费服务或多仓调度。

### 1. 六个业务域

本轮按以下六个业务域组织功能，其中支付属于交易域，选价属于活动域，库存属于仓储域：

| 业务域 | 项目中的功能 |
| --- | --- |
| 用户域 | 注册登录、个人信息、收货地址及用户身份 |
| 商品域 | 类目、商品、SKU、价格和上下架 |
| 交易域 | 购物车、订单、支付记录、取消与订单完成 |
| 活动域 | 活动配置、适用商品、优惠规则与选价 |
| 仓储域 | 默认仓库、SKU 库存、占用与释放、库存变化记录 |
| 履约域 | 订单后续处理、模拟备货与发货、完成状态查询 |

这里描述的是业务范围，不要求把六个域部署成六个服务。

### 2. 活动与价格：这次周边有优惠

管理员可以创建、修改和停用活动，设置活动名称、有效时间、参加活动的 SKU 及优惠规则。基础项目实现一种规则即可，例如指定 SKU 每件立减固定金额。

用户在商品详情和购物车中能够看到活动信息及价格，订单能够展示商品原价、优惠金额和应付金额。活动开始、结束或停用后，商城应展示对应的销售价格。

例如，一件原价 39 元的文化衫参加每件减 5 元的活动，购买两件时，商品原价合计 78 元、优惠 10 元、应付 68 元。未参加活动的商品仍按原价购买。

### 3. 支付：订单终于可以付款了

为订单增加支付能力。用户提交订单后可以发起付款，查看付款是否完成；管理员或开发者通过本地模拟入口产生支付成功、失败或延迟返回的结果。

支付记录需要能够关联订单，展示金额、付款时间、处理状态和模拟渠道的流水信息。用户可以在订单详情中查看对应的支付进度，付款结果也应反映到订单状态中。

模拟支付需要提供结果通知接口，可以人为重复发送通知或延迟发送结果，供整个项目联调和测试。它应当是一套可重复使用的本地模拟功能，不能只通过直接修改数据库演示“已付款”。

### 4. 仓库与库存：不能一直卖不存在的货

建立一个默认仓库，由管理员维护各 SKU 的库存，查询可售、已占用等数量及库存变化记录。

用户下单时占用本次购买所需的库存，付款完成后确认扣减；取消订单或超过约定时间仍未付款时，订单关闭，相关占用得到释放。库存不足时，用户能够知道本次购买未能完成。

例如，仓库中有 10 件文化衫，一个待付款订单购买 2 件后，其他用户还能购买剩余的 8 件。该订单取消后，这 2 件可以再次出售。

库存变化记录应能够查到关联订单、变动数量、时间和原因，便于运营人员确认货去了哪里。本轮不增加采购、调拨和盘点等仓库管理功能。

### 5. 履约：把订单送到终点

付款完成后，系统为订单生成后续履约任务。管理员可以查看待处理任务，模拟备货、发出和完成；用户可以查询自己订单的处理进度。

履约记录包含关联订单、需要处理的商品、收货信息和当前状态。模拟发货可以填写一个示例运单号，不需要调用真实物流平台。履约完成后，订单也应反映已经完成的结果。

至此，用户能从商品浏览、参加活动、加入购物车、提交订单走到付款和订单完成，也能结束一笔尚未付款的订单。所有操作都在同一个项目中连贯运行。

### 6. 后台工作：稍后完成的事也要有结果

在上述业务中落地异步处理，例如付款后的履约任务生成、订单通知或超时未付款订单的关闭。至少完成一条与真实订单关联的后台链路，不能只提交独立的线程或消息队列示例。

管理员应能够查看后台工作的处理进度和失败原因。暂时失败的工作支持重试，持续失败的工作有可查询的记录和重新处理入口；用户能够查询业务的最终结果。

运行中需要允许多个请求和多个后台任务同时执行。Java 方向应在实际功能中运用 JUC 的任务执行或并发协作能力；Go 方向使用对应的并发能力。任务执行方式、资源配置和消息组件由你结合项目决定。

### 7. 深入一个常见功能：让一部分经得起实际使用

基础商城跑通后，从电商常见功能中选择一个做深。这个专项属于本轮必做，可以深化已有功能，也可以增加一个紧密关联的小功能；它必须接入商城，复用已有用户、商品、订单和库存等能力。

推荐选择**限时秒杀**，也可以选择限量优惠券发放、热门商品库存抢购或订单超时处理。只选一个，不需要把所有方向都做一遍。

以秒杀为例，管理员能够配置活动时间、参与 SKU、活动价、名额和每人限购数量；用户在活动期间参与抢购，查询结果，获得购买资格后完成下单和付款。未开始、已结束、已售罄或超过限购的情况应有对应的用户反馈。取消或到期未付款时，按预先说明的活动规则处理资格与库存。

选择其他专项时，也要写清谁会使用、在什么条件下触发、能完成哪些操作，以及最终得到什么结果。复杂性集中在这一个专项中，其余业务域保持完整的基础能力即可。

这部分按可实际使用和维护的目标打磨：除了正常运行，还要能在约定的请求量、并发操作和故障场景下验证结果，出现问题后能够定位并恢复。说明部署条件、容量目标和已知限制，并保留可重复执行的测试与运行记录。

### 8. 压测与改进：人多起来以后会怎样

对所选专项的真实业务链路编写压测脚本，逐步增加负载，记录当前项目能承受的范围。先说明测试用户、商品和库存等数据如何准备，以及怎样判断一次操作完成，不能只测一个固定返回成功的空接口。

压测记录至少包括：

- 应用、数据库、消息组件和压测端的运行环境、资源配置及版本；
- 测试数据规模、请求速率或并发量、持续时间及业务结果；
- 吞吐量、P95/P99 延迟、技术错误与超时，以及售罄、限购等正常业务拒绝；
- CPU、内存和所选链路涉及的连接等待、任务积压等运行情况。

如果请求先被接收、稍后才完成，需分别记录接收响应和最终业务完成情况。通过日志或指标找到一个具体瓶颈，完成有依据的修改，再在相同条件下复测。保留脚本、原始结果和改进记录，说明哪些变化有效、哪些问题仍未解决。

同时为这条链路构造可重复的失败场景，例如模拟支付通知延迟、后台任务暂时失败或处理进程重启，观察失败与恢复过程。自动化测试继续覆盖功能及异常行为，优化后重新检查已有商城功能。

本轮不统一指定“必须达到多少 QPS”。性能目标需要结合实际机器、数据规模和业务操作说明；完成一次高吞吐演示，也不能直接等同于达到生产环境要求。

## 推荐技术栈与资料

沿用已有 Web 框架、数据访问方案和 MySQL。Docker Compose 配置同步包含实际使用的组件，项目能按 README 初始化、启动、测试和运行压测。

| 用途 | Java 路线 | Go 路线 |
| --- | --- | --- |
| Web 与数据访问 | Spring Boot，沿用当前持久化框架 | Hertz 或 go-zero，沿用当前数据访问库 |
| 并发与任务执行 | JUC：线程池、CompletableFuture、并发集合及同步工具，按实际需要选用 | goroutine、channel、context、sync |
| 异步消息 | RabbitMQ 或当前项目适用的成熟消息组件 | RabbitMQ 或当前项目适用的成熟消息组件 |
| 缓存 | Redis，按专项需要使用 | Redis，按专项需要使用 |
| 自动化测试 | JUnit 与现有接口测试工具 | Go 标准测试工具、竞态检测 |
| 压测 | k6 或 JMeter | k6 或 JMeter |
| 运行诊断 | JDK Flight Recorder、应用日志和指标 | pprof、应用日志和指标 |

以下资料按实际问题查阅，不要求把所有工具都用一遍：

- [Java 并发工具包官方文档](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html)：JUC 参考入口，使用其他 JDK 时切换到对应版本。
- [RabbitMQ Reliability Guide](https://www.rabbitmq.com/docs/reliability)：消息处理与故障相关的官方说明。
- [Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)：AWS 关于重试与接口设计的工程文章。
- [Grafana k6 文档](https://grafana.com/docs/k6/latest/)：负载脚本、指标和运行结果的参考。
