# learn-backend 第二轮考核：Web 基础与用户域

> 本轮从命令行程序进入 Web 后端开发。先通过 TodoList 掌握 HTTP、CRUD、数据库和分层，再重点完成用户从注册、登录到访问受保护资源的完整流程。

本轮支持 **Java** 和 **Go** 两条技术路线。Java 方向可以直接使用 Spring Boot，不要求先单独完成传统 Servlet/JSP 项目；但需要理解 HTTP、Cookie、Servlet 容器和请求处理流程等基础概念。Go 方向使用 Hertz 或 go-zero 框架

本轮暂不引入商品、购物车、订单等电商业务。TodoList 是独立的练习模块，用户域则会保留并继续用于后续业务项目。

## 任务

本轮分为三个阶段。请按顺序完成，每个阶段使用清晰的 Git Commit 或 Tag 留下可运行版本。

### 第一阶段：TodoList 与分层

实现一个 TodoList HTTP API，至少支持：

- 创建 Todo；
- 查询 Todo 列表与详情；
- 修改 Todo 的内容和完成状态；
- 删除 Todo；
- 对非法参数、数据不存在等情况返回明确错误。

Todo 至少包含标题、内容、完成状态和必要时间信息。具体接口路径和数据结构由你设计，并记录在 API 文档中。

#### 分层要求

建议调用方向如下：

```text
HTTP 请求
   ↓
Controller / Handler
   ↓
TodoService
   ↓
TodoRepository
   ↓
内存或 MySQL
```

- Controller/Handler 负责接收请求、参数校验和返回响应；
- Service 负责业务规则，不直接依赖 HTTP 请求或响应对象；
- Repository 负责数据读写，不负责决定业务流程；
- 不允许在 Controller/Handler 中直接拼接和执行 SQL；
- Todo 模块拥有自己的代码和数据访问边界。

这里的“独立 Service”指独立业务模块或服务层，**不是要求拆成单独部署的微服务**。后续移除 Todo 模块时，用户域和其他业务模块不应因此无法编译或运行。

建议先使用内存集合完成最小功能，再接入 MySQL。这样可以直接观察内存存储在重启、共享访问、数据约束和查询方面的限制。

### 第二阶段：用户注册与基础权限

实现以下用户能力：

- 用户注册；
- 用户登录和退出；
- 查询、修改自己的基本信息；
- 修改密码；
- 对需要登录的接口进行身份认证；
- 用户只能访问或修改属于自己的数据。

#### 注册流程

注册至少应包含以下步骤：

1. 接收并校验用户名、密码等注册信息；
2. 检查用户名、邮箱等业务标识是否重复；
3. 使用成熟的密码散列算法处理密码；
4. 在数据库中创建用户；
5. 返回不包含密码和密码散列的用户信息；
6. 对重复注册、非法参数和数据库失败返回明确结果。

用户名、邮箱等唯一性不能只依赖“先查询再插入”，还需要数据库唯一约束兜底。

#### 登录流程

登录至少应包含以下步骤：

1. 根据登录标识查询用户；
2. 使用密码散列库验证密码；
3. 创建对应认证方案的登录凭据；
4. 把凭据安全地返回给客户端；
5. 后续请求携带凭据；
6. 服务端验证凭据、过期时间和用户状态；
7. 将当前用户身份传递给业务代码；
8. 退出登录时使当前凭据失效或删除。

不存在的用户和密码错误不应向外暴露过多差异，日志中也不得记录明文密码和完整凭据。

#### 用户与 Todo 的连接

完成基础认证后，让 Todo 归属于当前用户：

- 创建 Todo 时从可信认证上下文获取用户 ID，不能信任请求体传入的用户 ID；
- 用户只能查询、修改和删除自己的 Todo；
- Todo 模块只依赖“当前用户身份”这一稳定输入，不直接操作用户模块内部的数据表或 Repository；
- 用户模块不能反向依赖 Todo 模块。

这个步骤用于验证身份认证、资源权限和模块解耦是否真正生效。

### 第三阶段：认证方案渐进实验

你需要理解以下三类方案，并通过 Git Commit 或 Tag 保存逐步实现过程。每个版本都应能够运行基本的登录、访问受保护接口和退出测试。

#### 版本一：签名 Cookie

Cookie 是浏览器保存并自动携带数据的机制，不是天然可信的身份认证方案。

- 不得把未经保护的 userId、用户名或 `isAdmin=true` 直接当作可信身份；
- Cookie 中的认证内容必须经过服务端签名或认证加密，篡改后应被拒绝；
- 使用框架或成熟安全库完成签名、验证和密钥管理，不自行设计加密算法；
- 根据运行环境设置 `HttpOnly`、`Secure`、`SameSite`、有效期等属性；
- 对依赖 Cookie 自动携带凭据的写操作，说明并处理 CSRF 风险；
- 需要说明退出登录和凭据撤销能力的限制。

该版本用于理解 Cookie 的传输行为和完整性保护，不代表最终项目必须选择它。

#### 版本二：Cookie + Session

- Cookie 只保存不可预测的 Session ID；
- 用户身份和过期时间保存在服务端 Session 中；
- 登录时创建 Session，退出时删除或失效；
- Session ID 需要防止会话固定攻击并在登录后更新；
- 需要处理过期 Session 和无效 Session；
- 可以先使用进程内存保存 Session，同时说明应用重启和多实例部署时的问题。

本轮不要求为了 Session 引入 Redis。后续学习缓存或多实例部署时再讨论集中式 Session。

#### 版本三：Token

- 登录成功后签发具有明确有效期的 Access Token；
- Access Token 可以是不透明随机 Token，也可以是经过签名的结构化 Token；需要说明自己的选择；
- 服务端验证签名、过期时间和必要声明；
- Token 中只保存必要信息，不放密码或敏感资料；
- 说明 Token 放在 `Authorization` Header 与放在 Cookie 中的安全差异；
- 说明退出、撤销和用户状态变化后旧 Token 仍可能有效的问题。

完成三个实验后，在主分支选择一种作为最终方案，并在 README 中说明选择理由。答辩时需要比较三种方案的状态保存位置、验证流程、退出方式、安全风险和扩展成本。

Access Token + Refresh Token、Refresh Token 轮换和无感刷新属于 Bonus。二维码登录、OAuth、单点登录等不在本轮范围内。

### 数据库与数据访问

#### 为什么需要 MySQL

内存集合适合快速完成 TodoList，但存在明显限制：

- 应用重启后数据丢失；
- 多个应用实例难以共享一致数据；
- 缺少唯一约束、关联约束和事务；
- 数据增多后查询、排序和分页难以维护；
- 并发修改时容易产生不一致。

MySQL 在本轮承担业务事实的持久化存储，用于保存用户、Todo，以及选择 Session 方案时可能需要持久化的会话数据。

你需要掌握：

- 表、字段和数据类型；
- 主键与唯一约束；
- 基本索引；
- 参数化增删改查；
- 事务的基本使用；
- 数据库迁移或建表脚本。

#### 为什么需要数据访问层或 ORM

业务代码不应到处处理连接、拼接 SQL、扫描结果和转换对象。独立的数据访问层可以隔离数据库细节，让业务逻辑更容易测试和替换。

ORM 可以完成对象与关系表之间的映射并减少重复代码，但会隐藏部分 SQL 行为；MyBatis 更接近 SQL Mapper，不属于完整 ORM。使用框架不能代替 SQL、索引、约束和事务知识。

常见选择包括：

- Java：JDBC、MyBatis/MyBatis-Plus、Spring Data JPA/Hibernate；
- Go：GORM（推荐）、Ent、`database/sql`、sqlx。

本轮不限定具体方案。你需要自己选择一种，并在 README 中说明：

- 是否需要手写 SQL；
- 为什么适合当前项目；
- 如何管理事务；
- 如何观察实际执行的 SQL；
- 相比其他方案放弃了什么。

需要提交可重复执行的数据库迁移或建表脚本。不能只提交数据库截图，也不能要求考核人员手工建表后才能启动项目。

### Docker 与开发环境

第二轮的核心是 Web、分层、用户认证和数据库，不应把编写复杂 Docker 配置作为必做内容。

建议由考核方提供一份经过验证的 `compose.yaml`，用于一键启动 MySQL。新人需要掌握：

- 使用 `docker compose up -d` 启动；
- 查看容器状态和日志；
- 理解端口映射、环境变量和数据卷；
- 使用 `docker compose down` 停止；
- 知道删除数据卷会造成数据丢失。

考核方提供的 Compose 文件应固定镜像版本、提供健康检查、使用本地开发凭据，并写明数据清理方式。没有 Docker 运行条件时，可以使用本地 MySQL，但启动和初始化过程仍需可复现。

新人自行编写应用 Dockerfile、把应用与 MySQL 一起编排，作为 Bonus 或后续轮次内容。

## 提示

- 不要把 Cookie、Session 和 Token 当成三个互斥名词；Cookie 常常负责携带 Session ID 或 Token；
- 普通 Cookie 中的 userId 可以被客户端修改，不能直接作为可信身份；
- 密码应使用成熟的密码散列方案，不要自行设计加密算法；
- 认证只说明“你是谁”，资源权限还需要判断“你能否操作这条数据”；
- 先使用内存实现 Todo，再接入 MySQL，更容易理解数据库带来的价值；
- Service 负责业务规则，Repository 负责数据访问，框架不能代替边界设计；
- ORM 和 SQL Mapper 会减少样板代码，但仍需观察和理解实际 SQL；
- Java 方向可以直接学习 Spring Boot，不需要先完整学习 Servlet/JSP；
- AI 适合讲解、提问和排错，不适合替你决定未经验证的安全方案；
- README 中应如实标注未完成内容和已知问题。
