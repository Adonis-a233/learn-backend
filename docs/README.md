## 四阶段递进关系

```text

    ↓

    ↓
```

## 通用规则

### 必做、Bonus 与非目标

- 各轮项目描述中的基本功能与明确要求是本轮必做；
- Bonus 只能在必做内容完成后选择，不用于抵消缺失的核心功能；
- 文档明确列出的非目标不需要提前实现；
- 如果确实无法完成某项要求，应在 README 中列出未完成内容、原因和当前结果，禁止伪造演示或测试记录。

### 技术选择

- 选择仍在维护、有官方文档并适合团队评审的语言和框架；
- 同一项目中保持主要技术栈稳定，确需更换时说明原因、迁移范围和验证方式；
- 数据库、缓存、消息队列、搜索引擎或 Agent 必须对应明确问题，不按组件数量评分；
- 金额、库存、权限和状态流转等规则必须由确定性后端代码校验，不能交给客户端、提示词或人工约定。

### 代码与安全

- 禁止提交真实密钥、访问令牌、生产数据或无法公开的个人信息；
- 密钥和环境差异使用环境变量或配置示例管理；
- 密码不得明文存储，用户只能访问自己有权限的数据；
- 依赖和运行时版本应固定到可复现范围；
- 生成代码和 AI 辅助代码也必须能够独立解释、修改和调试。

## 提交通则

当届负责人统一发布报名、评审或汇总提交入口；学习者须将项目仓库链接提交到该入口。第一轮须由学习者自行创建一个公开 GitHub 仓库，并将完整命令行项目推送到该仓库。第二轮至第四轮建议在同一公开仓库中持续迭代，并为每轮创建可追溯的 Git 标签或 Release：

```text
learn-backend-<github-id>/
├─round-1/              # 第一轮独立命令行项目
└─ecommerce/            # 第二至第四轮持续迭代
```

每轮至少提交：

- 源代码和依赖配置；
- README 与本轮完成情况；
- 可复制的启动、测试和停止步骤；
- 数据库迁移或初始化方案；
- 自动化测试及必要的测试数据；
- API 文档、设计图或测试报告等本轮要求的产物；
- `.gitignore` 和不含真实凭据的配置示例。

第一轮的公开仓库还必须包含完整源码、题目提供的固定数据包、依赖配置、README 和测试；仅上传 jar、截图或运行结果不视为提交。固定数据包的来源、数据格式、目录结构、版本和完整性校验见 [`data/round-1-diving-2026/`](../data/round-1-diving-2026/)。

从空环境按 README 无法启动和验证的项目，不视为完整交付。

## 关于答辩

第二轮至第四轮原则上需要答辩，具体安排以当届通知为准。答辩时间与作品提交截止时间应至少错开一天，给考核人员预留检查时间。

答辩关注以下内容：

1. 演示本轮核心成功路径和规定的失败路径；
2. 解释业务规则、数据归属、状态流转和异常处理；
3. 说明测试如何证明结果，而不是只展示接口返回成功；
4. 解释关键技术选择、替代方案和已知限制；
5. 现场定位或修改一处小问题，确认提交者理解代码；
6. 主动说明未完成内容，不需要用复杂 PPT 包装。

如果遇到技术困难、设备限制或时间冲突，应尽早联系负责人，并提供当前代码、错误信息和已经尝试的方法。负责人可以调整时间或缩小 Bonus，但不应在不同成员之间改变核心验收标准。

## 评价原则

评价优先级依次为：

1. 正确性、权限与数据安全；
2. 可运行、可测试和可复现；
3. 业务建模与异常路径；
4. 模块边界、代码可维护性和协作说明；
5. 性能、可靠性与拓展深度。

框架更新、服务数量、代码行数和中间件数量都不是独立加分项。未经测量的“性能优化”、没有故障验证的“高可用”和无法说明数据来源的测试数字不作为有效证据。
