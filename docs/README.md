# learn-backend 考核文档

本目录包含西二在线工作室 learn-backend 后端方向的推荐资料和五轮考核。第一轮用于掌握一门编程语言并完成独立命令行项目；第二轮通过 TodoList 和用户域建立 Web 后端基础；第三轮起持续开发电商业务。

### Prompts 使用说明

`prompts/round2/`、`prompts/round3/` 和 `prompts/round4/` 中的文件是学习辅助材料，用于解释原理、设计练习和评审实现。建议按照学习进度逐个使用。

1. `prompt1.md`：制定学习阶段和每阶段的输出，明确当前环境与学习边界；
2. `prompt2.md`：通过创建和查询 Todo，理解 HTTP、CRUD、分层以及依赖方向；
3. `prompt3.md`：比较 Cookie、Session、Token 等认证方案，理解请求流程、安全风险和适用场景；
4. `prompt4.md`：从进程内集合迁移到 MySQL，学习持久化需求和当前语言对应的数据访问方案；
5. `prompt5.md`：遇到后端问题时先收集事实、建立假设并执行最小实验，确认根因后再修改代码。

这些 prompt 的共同约束是：导师负责解释原理、比较方案、设计练习和检查理解，不直接代写完整项目；学习者仍需独立完成代码、测试、调试和最终说明。使用时应补充日期、语言、框架、版本和已有实现等环境信息，并对生成的建议进行实际验证。

## 五轮递进关系

```text
语言与文件处理
    ↓
TodoList、分层、数据库、用户注册与认证
    ↓
商品与 SKU、购物车、订单与取消
    ↓
模块边界、业务事件、后台任务、重复处理与失败恢复
    ↓
压测与 SQL 优化、可观测性、可靠性验证、业务专项拓展
```

第二轮建立的用户域必须延续到后续业务项目；TodoList 保持独立边界，后续可以移除。每轮可以重构前一轮代码，但不能通过增加新技术掩盖尚未解决的正确性问题。

## 通用规则

### 必做、Bonus 与非目标

- “任务”和“验收标准”中的内容是本轮必做；
- Bonus 只能在必做内容完成后选择，不用于抵消缺失的核心功能；
- 文档明确列出的非目标不需要提前实现；
- 如果确实无法完成某项要求，应在 README 中列出未完成内容、原因和当前结果，禁止伪造演示或测试记录。

### 技术选择

- 选择仍在维护、有官方文档并适合团队评审的语言和框架；
- 同一项目中保持主要技术栈稳定，确需更换时说明原因、迁移范围和验证方式；
- 数据库、缓存、消息队列、搜索引擎或 Agent 必须对应明确问题，不按组件数量评分；
- 金额、库存、权限和状态流转等规则必须由确定性后端代码校验，不能交给客户端、提示词或人工约定。

### 代码与安全

- 禁止提交真实密钥、访问令牌、生产数据或无法公开的个人信息；
- 密钥和环境差异使用环境变量或配置示例管理；
- 密码不得明文存储，用户只能访问自己有权限的数据；
- 依赖和运行时版本应固定到可复现范围；
- 生成代码和 AI 辅助代码也必须能够独立解释、修改和调试。

## 提交通则

第二轮至第五轮建议使用同一个项目目录，并为每轮创建可追溯的 Git 标签或 Release：

```text
learn-backend-<github-id>/
├─round-1/              # 第一轮独立命令行项目
└─ecommerce/            # 第二至第五轮持续迭代
```

每轮至少提交：

- 源代码和依赖配置；
- README 与本轮完成情况；
- 可复制的启动、测试和停止步骤；
- 数据库迁移或初始化方案；
- 自动化测试及必要的测试数据；
- API 文档、设计图或测试报告等本轮要求的产物；
- `.gitignore` 和不含真实凭据的配置示例。

从空环境按 README 无法启动和验证的项目，不视为完整交付。

## 关于答辩

第二轮至第五轮原则上需要答辩，具体安排以当届通知为准。答辩时间与作品提交截止时间应至少错开一天，给考核人员预留检查时间。

答辩关注以下内容：

1. 演示本轮核心成功路径和规定的失败路径；
2. 解释业务规则、数据归属、状态流转和异常处理；
3. 说明测试如何证明结果，而不是只展示接口返回成功；
4. 解释关键技术选择、替代方案和已知限制；
5. 现场定位或修改一处小问题，确认提交者理解代码；
6. 主动说明未完成内容，不需要用复杂 PPT 包装。

如果遇到技术困难、设备限制或时间冲突，应尽早联系负责人，并提供当前代码、错误信息和已经尝试的方法。负责人可以调整时间或缩小 Bonus，但不应在不同成员之间改变核心验收标准。

## 评价原则

评价优先级依次为：

1. 正确性、权限与数据安全；
2. 可运行、可测试和可复现；
3. 业务建模与异常路径；
4. 模块边界、代码可维护性和协作说明；
5. 性能、可靠性与拓展深度。

框架更新、服务数量、代码行数和中间件数量都不是独立加分项。未经测量的“性能优化”、没有故障验证的“高可用”和无法说明数据来源的测试数字不作为有效证据。
